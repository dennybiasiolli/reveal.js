Handling time in software seems simple, until it isn't. From daylight savings quirks to database inconsistencies and user-local conversions, timezones can quietly turn into one of your biggest sources of bugs. In this talk, we'll unravel the paradox of time in Python and Django: how something so universal can be so tricky to get right. You'll learn how Django handles datetime objects, the difference between naive and aware datetimes, common pitfalls when working with ORM and serializers, and best practices for ensuring your applications stay consistent across users, systems, and regions. By the end, you'll be equipped with practical techniques and mental models to make your Django apps truly timezone-safe, and your logs, reports, and users finally in sync.

A Story from the Finance Team

April 1, 2026, 4:52 PM CET

The Head of Finance in New York
joins the Q1 close call

Why is our US East Coast revenue
$2.3 million lower than expected?

47 large March 31 payments never made it into Q1
No, it's not an April Fool's joke

$2.3M just disappeared from Q1

  • Wrong tax provisions and revenue recognition
  • Payments (and sales commissions) booked in Q2
  • Financial statements don't match the Q1
  • Board deck and auditors start asking hard questions
The root cause: `paid_at` is the correct business timestamp — the exact moment the money was received or the transaction was confirmed. Finance uses it for revenue recognition, cash reporting, tax periods, and commission calculations.

But `TruncQuarter()` / `date_trunc('quarter')` and Django's Trunc* functions are timezone-sensitive. They use the *current session/database timezone*, not the timezone in which the payment actually happened.

A March 31 11:17 PM payment in New York becomes April 1 in UTC/Europe → leaks into the next quarter in every grouped report.

This is why "just store everything as timestamptz" is not enough when finance needs calendar-based grouped reports.

The query Finance trusted

# Quarter Revenue & Cash Report (board + tax + commissions)

# received as parameters
quarter_start = "2026-01-01"
quarter_end   = "2026-04-01"

qs = (Payment.objects
    .filter(paid_at__gte=quarter_start,
            paid_at__lt=quarter_end)
    .annotate(quarter=TruncQuarter("paid_at"))
    .values("quarter")
    .annotate(total=Sum("amount"))
)

Simple. Correct. Obviously right.
Trusted by the CFO, controllers, and the entire finance team.

Example of a payment
that leaked into Q2

A customer in New York pays $340k
on March 31 at 20:17 PM local time

Recorded correctly as
paid_at 2026-03-31 20:17:00-04:00

All the queries on the server run in UTC
and classify the payment as 2026-Q2

Same payment. Same database. Different quarter.

-- paid_at = 2026-03-31 20:17:00-04:00

-- what users expect in New York
SET TIMEZONE TO 'America/New_York';
SELECT date_trunc('quarter', paid_at);
-- 2026-Q1

-- what the server has in UTC
SET TIMEZONE TO 'UTC';
SELECT to_char(paid_at, 'YYYY-"Q"Q');
-- 2026-Q2
  • paid_at never changes
  • Every single paid_at value we display in the frontend (API+JSON)
    is formatted by the browser using the user's local timezone
  • The dashboard summary is generated server-side
    using the server timezone
This is the database inconsistency. timestamptz stored the instant correctly. date_trunc / Trunc* answer in the current session timezone. Django will do SET LOCAL TIMEZONE for you later — that's the payoff.

The Two Faces of Time

(that look identical until they aren't)

  1. Recording the past (or present)
    order created, log entry, error occurred
  2. Scheduling the future
    reminder, report, recurring task

Recording when something happened:
Record in UTC

UTC is the universal reference time,
it never shifts for daylight saving

  • Unambiguous, always the same reference point
  • Convertible to any local timezone
  • The right choice for anything that already happened

UTC is the boring reliable friend who never cancels plans
Appreciate UTC

Scheduling when something should happen:
Store the intent

Finance doesn't want the daily report at 14:00 UTC

They want it at 9:00 AM in their day,
every single day, regardless of UTC offset

If you store a fixed UTC time and DST changes, the report suddenly runs at the wrong local time

Instead, store 09:00 America/New_York
and recalculate the actual UTC execution time

The intent stays constant
The UTC execution time adapts

UTC-5 ≠ America/New_York

UTC-5 (fixed offset) America/New_York (timezone)
The offset at one specific instant A set of rules that change over time
Always UTC-5, forever UTC-5 Nov-Mar, UTC-4 Mar-Nov
→ Use timezone identifiers, not fixed offsets
These rules live in the IANA Time Zone Database (TZDB), the standard used by every OS and language.

IANA Time Zone Database

The standard behind every OS
and programming language

Defines rules for every timezone:
DST start/end, offsets, historical changes

In 2011, Samoa skipped an entire day (Dec 30th) by moving across the date line.
Someone had to update this database. Imagine the commit message

DST creates two tricky edge cases

(DST was invented by someone who hates programmers)

  1. Spring forward — the clock skips an hour
  2. Fall back — the clock repeats an hour

1. Spring Forward: the phantom hour

In New York, DST starts on March 9, 2026 at 2:00 AM

The clock jumps: 1:59:59 AM → 3:00:00 AM

2:30 AM on March 9, 2026 never happened

Some libraries throw. Others silently move you to 3:30.
Know what yours does, and warn the user.

2. Fall Back: the duplicate hour

In New York, DST ends on Nov 2, 2026 at 2:00 AM

The clock jumps back: 1:59:59 AM → 1:00:00 AM

1:30 AM happens twice

If it's your alarm clock, pick the second one.
You deserve the extra sleep.

Days aren't always 24 hours

  • March 9, 2026 in New York: 23 hours long
  • November 2, 2026 in New York: 25 hours long

This matters when scheduling the next run:

# skips/repeats the DST hour
next_run = now + timedelta(hours=24)

# respects the local calendar day
next_run = now + timedelta(days=1)

Timezone in Python

datetime object

  • naive, no timezone information
    using the system's local timezone
  • aware, with timezone information
    using the specified timezone

A naive datetime assumes everyone works in the same timezone,
like people who think it's always sunny everywhere
because it's sunny outside their window

Example

from datetime import datetime
from zoneinfo import ZoneInfo # Python 3.9+

# Naive, 09:00 local timezone
datetime(2026, 10, 26, 9, 0)  # try to avoid this

# Aware, 09:00 in New York
datetime(2026, 10, 26, 9, 0,
         tzinfo=ZoneInfo("America/New_York"))

Timezone in PostgreSQL

timestamptz column

  • Short name for timestamp with time zone
  • Doesn't store the timezone itself
  • Normalizes the timestamp to UTC upon storage
  • Converts it back to the desired timezone upon retrieval

Postgres can set the timezone in six different places.
Server level, connection string, database, user, session, transaction.
Django uses the last one: 

SET LOCAL TIMEZONE TO '<SERVER_TIMEZONE_HERE>';

Per transaction. Per query. That's the lever behind the $2.3M slide.

Django

Django has built-in support for timezones

You can enable it in your settings with

USE_TZ = True

All DateTime fields will be stored in UTC in the database and will be converted to the active timezone when retrieved

Django Timezone setting

You can set the default timezone for your Django application using the TIME_ZONE setting 

TIME_ZONE = "UTC"

By default, it's set to UTC, but you can change it to any valid timezone string

PostgreSQL + Django

When USE_TZ is enabled
Django wraps each query in a transaction that sets
SET LOCAL TIMEZONE
to the currently active timezone

The Problem in all of this

All users will see timestamps in the same timezone set in TIME_ZONE, regardless of their location

And that timezone will be used to query the database too

😞

Same report. New York time.

from zoneinfo import ZoneInfo
from django.utils import timezone

timezone.activate(ZoneInfo("America/New_York"))

Payment.objects.filter(
    paid_at__gte="2026-01-01",
    paid_at__lt="2026-04-01",
)
# March 31, 20:17 in New York stays in Q1
# Nobody memorized an offset

Ship the combination. That's the middleware.

Django Middleware solution

import zoneinfo
from django.utils import timezone

if request.user.is_authenticated:
    tzname = request.user.profile.timezone
else:
    tzname = (request.headers.get("X-Timezone")
              or request.COOKIES.get("django_timezone"))

if tzname:
    timezone.activate(zoneinfo.ZoneInfo(tzname))

Django then converts timestamps to that timezone on the way out.
Cookie, header, and curl examples are in the repo.

Three rules to live by

1. Use timezone-aware datetimes

Don't use naive datetimes, or you'll have to do timezone math manually

And timezone math is not real math!

2. Store in UTC, display in local time

UTC is the reliable, unambiguous way
to store timestamps

Local time is what users expect to see

That includes your logs.
[2026-03-31 20:17:00] payment received $340k
[2026-04-01 00:17:00Z] payment received $340k
If it doesn't say Z, every post-mortem is a timezone puzzle.

Logs are just another recording of the past. UTC in the database and the logs. Local time for users. An explicit timezone for reports. Then the three of them finally agree.

3. Ask for the timezone for sensitive operations
(like fiscal reports)

Don't rely on the server's timezone
or a fixed timezone for all users

Remember: timezone math is not real math!
